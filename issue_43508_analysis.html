中文标题：混合 Mamba 模型 + KV Connector 分离式部署被 _mamba_block_aligned_split 断言阻断

原始链接：github.com/vllm-project/vllm/issues/43508

✅ 最终状态：自行修复（Self-Resolved）

一句话总结：当运行 Hybrid Mamba 模型（如 NemotronH-550B / Jamba）且同时启用 Mamba 对齐缓存模式 mamba_cache_mode="align" 与外部 KV Connector（如 NixlConnector）时，调度器中一个无条件断言会导致 EngineCore 子进程在第一个推理请求到达时立即崩溃，使这类模型无法使用 vLLM 的分离式（Disaggregated）服务。

一、复现环境

组件 具体配置
vLLM 版本 0.19.0（验证 main 与 v0.21.0 也存在此问题）
运行镜像 nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.0.1（dynamo-vllm-efa）
硬件 2 × p5en.48xlarge（总计 16 × H200 GPU），EFA 互联
目标模型 nvidia/Nemotron-3-Ultra-550B-A55B-RL（NemotronH SSM-Hybrid，Mamba + Attention + MoE，550B 参数）
部署拓扑 分离式服务（Disaggregated Serving）：LeaderWorkerSet 2 节点
  • 1 个 Prefill Leader（--disaggregation-mode prefill）
  • 1 个 Decode Leader（--disaggregation-mode decode）
KV 传输层 NixlConnector + NIXL + LIBFABRIC transport（EFA RDMA）
关键启动参数 --no-disable-hybrid-kv-cache-manager（启用混合 KV 缓存管理器）
mamba_cache_mode == "align"（Mamba 缓存对齐模式）

二、Bug 现象与触发位置

2.1 触发断言的代码位置

在文件 vllm/v1/core/sched/scheduler.py 的函数 _mamba_block_aligned_split 中，存在一条无条件断言：

assert num_external_computed_tokens == 0, \
    "External KV connector is not verified yet"

2.2 崩溃流程

请求到达 Frontend
→
请求进入 Decode Leader
→
调度器 _mamba_block_aligned_split
→
断言失败 ❌
EngineCore 子进程崩溃

2.3 直接影响

  • 任何 Mamba-Hybrid 家族模型（Jamba、NemotronH 等）在 stock vLLM 中完全无法进行分离式服务
  • 请求永远无法完成 —— 崩溃发生在第一个请求到达调度器的瞬间
  • 即使已经正确配置 NixlConnector / Hybrid KV cache 也无济于事

三、根因分析

3.1 断言存在的原因

该断言的注释表明：开发者在实现 Mamba 对齐缓存分割逻辑时，尚未验证外部 KV Connector（通过 num_external_computed_tokens > 0 表示有外部已计算的 KV tokens 需要处理）场景下的正确性，因此暂时用断言阻断了此路径。

3.2 为什么会触发

分离式服务模式下：

  1. Prefill Leader 完成预填充后，通过 NixlConnector 将 KV Cache 传递给 Decode Leader
  2. Decode Leader 收到的请求带有「外部已计算的 tokens」（num_external_computed_tokens > 0）
  3. 调度器调用 _mamba_block_aligned_split 对 Mamba SSM 状态做块对齐分割
  4. 断言直接被触发，进程崩溃

3.3 触发条件的组合（必须同时满足）

✅ 条件全部满足才会触发

  • Hybrid Mamba 模型（SSM + Attention 混合架构）
  • mamba_cache_mode == "align"
  • 外部 KV Connector 启用（NixlConnector 等）
  • 分离式服务（Prefill/Decode 分离）或 KV offload

⚠️ 相似但不同的触发路径

Issue #41515 报告了相同的断言，但是：

  • 场景：kv_offload + HMA
  • 时机：后续请求（非首个）
  • 模型：非 NemotronH

四、复现步骤

  1. 部署 2 节点 LWS 拓扑：1 个 Prefill Leader + 1 个 Decode Leader
    • 模型：nvidia/Nemotron-3-Ultra-550B-A55B-RL
    • 分别设置 --disaggregation-mode prefill 和 --disaggregation-mode decode
    • 启用混合 KV 缓存管理器：--no-disable-hybrid-kv-cache-manager
    • 配置 NIXL + LIBFABRIC Connector（rev7 NIXL config）
  2. 等待就绪：确认两个 Leader 都达到 Ready 状态
  3. 发送请求：通过 Frontend 发送一个简单的 chat completion 请求
  4. 观察结果：Decode Leader 的 EngineCore 子进程立即因上述断言崩溃，请求永不完成

五、验证过程与修复方案

5.1 现有的修复尝试（PR #42522）

此问题与 PR #42522 试图解决的 Jamba 问题完全相同。该 PR 因「过旧（stale）」被关闭，但代码并未合入主线。

5.2 修复思路（#42522 的做法）

修改文件 vllm/model_executor/models/config.py：当角色为 KV 消费者（is_kv_consumer = True）时，将 mamba_block_size 设置为 max_model_len，从而跳过有问题的对齐分割路径。

# 核心逻辑简化示意
if is_kv_consumer and mamba_cache_mode == "align":
    mamba_block_size = max_model_len  # 整个模型长度作为一个块，跳过分割
else:
    mamba_block_size = original_calculated_value  # 走原对齐逻辑

九、结论与要点

  • 问题本质：调度器中的防御性断言未考虑外部 KV Connector 与 Mamba 对齐模式共存的场景，属于「未验证路径先阻断」的设计。
  • 影响范围：所有 Hybrid Mamba 架构模型（Jamba、NemotronH 系列）+ 任何使用外部 KV Connector 的分离式或 KV Offload 部署。
  • 短期缓解：对需要立即使用的用户，cherry-pick PR #42522 的 commit c27097c762934c23a454736d32a090c4708dadb8 到目标版本即可。
  • 长期解决：
    • PP=1：按 #42522 的 mamba_block_size = max_model_len 分支合并到主线
    • PP>1：通过 #48263 修复去重池成员恢复逻辑
  • 对 vLLM 开发者的教训：未来加入临时断言时应提供更细的 Feature Flag 或 Runtime Option，让高级用户可选择性关闭（而非硬崩溃）。
