PART 1

概念基础

先理解 PD 分离解决什么问题、涉及哪些核心概念，再进入架构与流程细节。

1.1 什么是 PD 分离

PD 分离（Prefill-Decode Disaggregation）把一次推理请求的生命周期切成两段，由不同硬件实例承担：

  • P 节点（Prefiller）：专门处理 prefill 阶段，对完整 prompt 做并行计算，生成 KV Cache，只输出 1 个 token。
  • D 节点（Decoder）：专门处理 decode 阶段，从 P 节点拉取 KV Cache 后逐 token 自回归解码。

两节点之间通过 Mooncake TransferEngine（RDMA/P2P）传递 KV Cache，避免重算。

1.2 为什么需要 PD 分离

传统连续批处理（CB）中 prefill 与 decode 混跑，存在三类痛点：

  • 计算资源竞争：prefill 是计算密集型（长 prompt 并行），decode 是访存密集型（短输入），同一 GPU 同时优化两者困难。
  • 延迟互相干扰：长 prefill 会阻塞 decode，导致已生成 token 的 TPOT 抖动。
  • 并行策略冲突：prefill 偏好 TP/PP，decode 偏好 DP，单实例难以兼顾。

PD 分离让 P / D 节点各自选择最优并行策略与实例数量，分别优化 TTFT 与 TPOT；KV Cache 通过高速互联在 P/D 间传输，消除重算开销。

def request_finished(self, request, block_ids):
    params = request.kv_transfer_params
    # 仅当 do_remote_decode=True 且状态为 FINISHED_LENGTH_CAPPED 时延迟释放
    if not params.get("do_remote_decode") or request.status != FINISHED_LENGTH_CAPPED:
        return False, None

    num_prompt_blocks = math.ceil(len(request.prompt_token_ids) / self.block_size)
    computed_block_ids = self._get_transfer_block_ids(block_ids, len(request.prompt_token_ids))
    computed_block_ids = self._get_swa_transfer_block_ids(computed_block_ids)
    delay_free_blocks = sum(len(b) for b in computed_block_ids) > 0

    if delay_free_blocks:
        self._reqs_need_send[request.request_id] = time.time()

    # 返回 kv_transfer_params 给代理
    return delay_free_blocks, dict(
        do_remote_prefill=True,           # D 节点需要拉取
        do_remote_decode=False,
        remote_block_ids=computed_block_ids,
        remote_engine_id=self.engine_id,
        remote_host=self.side_channel_host,
        remote_port=self.side_channel_port,
        remote_pcp_size=self.pcp_size,
        remote_dcp_size=self.dcp_size,
        remote_ptp_size=self.tp_size,
        last_token_id=request.output_token_ids[-1],
        num_prompt_blocks=num_prompt_blocks,
        remote_block_size=self.block_size,
    )

_submit_request（L628）—— 按远端地址分派

def _submit_request(self, request_data):
    peer_key = (request_data["remote_host"], request_data["remote_handshake_port"])
    self._mark_request_task_submitted(request_data)  # 计数+1
    should_start_worker = False
    with self.peer_request_queues_lock:
        self.peer_request_queues[peer_key].append(request_data)
        if peer_key not in self.active_peer_request_handlers:
            self.active_peer_request_handlers.add(peer_key)
            should_start_worker = True
    if should_start_worker:
        self.executor.submit(self._handle_peer_requests, peer_key)

_handle_peer_requests（L641）—— 批量消费

def _handle_peer_requests(self, peer_key):
    requests_handled = 0
    while requests_handled < MAX_REQUESTS_PER_PEER_HANDLER:
        with self.peer_request_queues_lock:
            peer_queue = self.peer_request_queues.get(peer_key)
            if not peer_queue:
                self.active_peer_request_handlers.discard(peer_key)
                return
            req_meta = peer_queue.popleft()
        requests_handled += 1
        self._handle_request(req_meta)   # 真正传输

    # 队列非空则重新提交自己
    if should_resubmit:
        self.executor.submit(self._handle_peer_requests, peer_key)

def run_busy_loop(self, sock):
    while True:
        frames = sock.recv_multipart()
        identity = frames[0]
        msg = decoder.decode(frames[1])
        if msg[0] == GET_META_MSG:
            # D 节点请求元数据 → 返回 MooncakeAgentMetadata
            sock.send_multipart((identity, b"", encoded_data))
        elif msg[0] == DONE_RECVING_MSG:
            # D 节点通知接收完成 → 释放 KV 块
            request_id = msg[1]
            self.task_tracker.update_done_task_count(request_id)
            sock.send_multipart((identity, b"", b"ACK"), flags=zmq.NOBLOCK)

PART 4

核心机制深度解析

把第三部分提到的「异步队列」与「KV 传输」单独展开，并补充错误处理与重试策略。这是 PD 分离实现的关键所在。

4.1 异步队列机制（三级流水线）

KVCacheRecvingThread 使用三级队列 + 线程池实现高并发下的 KV 拉取，避免单线程瓶颈。

图 4-1：KVCacheRecvingThread 三级队列流水线

为什么需要三级队列？

  • 第一级 request_queue：单线程消费，作为入口缓冲，避免上游阻塞。
  • 第二级 peer_request_queues：按 (remote_host, remote_handshake_port) 分桶，同一 P 节点的请求串行化，避免并发 ZMQ 握手冲突；不同 P 节点之间仍可并发。
  • 第三级 ThreadPoolExecutor：每个 peer 一个 handler 线程，批量处理 MAX_REQUESTS_PER_PEER_HANDLER 个请求后重新自提交，保证持续消费。

任务计数与完成判定

def _mark_request_task_submitted(self, req_meta):
    request_id = req_meta["request_id"]
    with self.request_task_counts_lock:
        self.request_task_counts[request_id] += 1
        if req_meta["all_task_done"]:
            self.finished_request_markers.add(request_id)

def _mark_request_task_done(self, request_id, all_task_done) -> bool:
    with self.request_task_counts_lock:
        pending_count = self.request_task_counts.get(request_id)
        if pending_count is None: return all_task_done
        pending_count -= 1
        if pending_count > 0:
            self.request_task_counts[request_id] = pending_count
            return False  # 还有未完成的 shard
        # 全部完成
        self.request_task_counts.pop(request_id, None)
        has_finished_marker = request_id in self.finished_request_markers
        self.finished_request_markers.discard(request_id)
        return has_finished_marker

设计要点：并发度 vs 一致性

  • 串行化粒度：peer 级别，保证同一 P 节点的 ZMQ 会话不交错。
  • 并发度：不同 peer 之间完全并发，受 max_workers=32 限制。
  • 批量上限：MAX_REQUESTS_PER_PEER_HANDLER 防止单个 handler 独占线程池过久，强制让出。
  • 重入机制：handler 处理完一个批次后，若队列非空则 self.executor.submit(self._handle_peer_requests, peer_key) 自递归。

P 节点延迟释放与超时兜底

def _retrieve_expired_requests(self):
    expired_requests: set[str] = set()
    current_time = time.time()
    while self.delayed_free_requests:
        request_id = next(iter(self.delayed_free_requests))
        delay_start_time = self.delayed_free_requests[request_id]
        if current_time - delay_start_time > envs.VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT:
            # 超时强制释放, 防止 D 节点崩溃导致 P 节点内存泄漏
            self.delayed_free_requests.popitem(last=False)
            self.reqs_to_process.discard(request_id)
            expired_requests.add(request_id)
        else:
            break
    return expired_requests

超时兜底是关键防泄漏机制：若 D 节点崩溃不发 DONE_RECVING_MSG，P 节点会按超时强制释放 KV 块，避免内存被永久占用。
