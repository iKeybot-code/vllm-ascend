1. 概述与发展背景

混合专家模型（Mixture of Experts, MoE）是一种通过"条件计算"实现模型容量扩展的神经网络架构。与传统稠密网络不同，MoE 为每个输入只激活部分参数，从而在显著增加总参数量的同时，控制每次前向传播的实际计算量。

MoE 的核心动机源于大模型训练中的两个矛盾：

  • 容量需求：模型需要足够多的参数来学习海量知识；
  • 计算约束：每次推理的计算成本必须可控，不能随参数线性增长。

在 Transformer 时代，MoE 最成功的应用是替代 Decoder/Encoder 层中的前馈网络（FFN）。代表工作包括 GShard、Switch Transformer、DeepSeek-V2/V3 等，它们将 MoE 推向了千亿乃至万亿参数规模。

2. 网络结构

一个标准的 MoE 层由三个核心组件构成：多个专家网络（Experts）、一个门控网络（Gating Network / Router），以及 Top-K 选择器。下图展示了一个典型 MoE 层的内部结构。

2.1 专家网络（Experts）

每个专家通常是一个独立的前馈网络（FFN），结构与标准 Transformer 中的 FFN 相同。在语言模型中，不同专家可能分别擅长语法、事实知识、代码、推理等不同模式。

2.2 门控网络（Router）

门控网络是一个轻量级的线性层，输入为 hidden states，输出为每个专家的得分。经过 Softmax 后得到概率分布，表示当前输入应该分配给哪些专家。

2.3 Top-K 选择器

从所有专家的概率分布中选取前 K 个。K 通常取 1、2 或 4。K=1 时称为 Switch Transformer 风格，K=2 是目前大模型中最常见的配置。

3. 核心技术特点

稀疏激活

虽然模型总参数量巨大，但每个 token 只激活 K 个专家，实际计算量约等于 K 个单专家前向传播之和。

条件计算

网络根据输入内容动态选择计算路径，不同 token 走不同专家，实现"按需计算"。

Top-K 路由

通过门控网络的 Softmax 分数进行排序，只保留前 K 个专家参与计算，其余专家完全不被激活。

负载均衡

通过辅助损失函数或动态偏置，避免所有 token 都涌向少数"热门"专家，保证各专家负载均衡。

容量因子

限制每个专家在单位批次内能处理的 token 数，超出容量的 token 会被溢出处理，平衡计算与内存。

专家并行

将不同专家分布到不同计算设备上，通过 All-to-All 通信实现 token 路由与结果聚合。

4. 数学原理

设输入为 x ∈ R^d，专家数量为 N，每个专家的输出为 E_i(x)，门控网络输出为 g(x) ∈ R^N。

4.1 门控分数

g(x) = Softmax(W_g · x) ∈ R^N

其中 W_g ∈ R^(N×d) 是门控网络的权重矩阵。

4.2 Top-K 选择与归一化

G(x)_i = { g(x)_i, if i ∈ TopK(g(x), K);
              0,         otherwise }

通常会对选中的 K 个权重再次归一化，使得 Σ w_i = 1。

4.3 MoE 层输出

y = Σ_{i ∈ TopK(g(x), K)} G(x)_i · E_i(x)

只有被 Router 选中的专家才会参与最终输出的计算。

4.4 负载均衡损失

GShard 提出的辅助损失用于鼓励 token 均匀分布到各专家：

L_load = N · Σ_{i=1}^{N} f_i · P_i

其中 f_i 是实际分配给专家 i 的 token 比例，P_i 是门控网络对专家 i 的平均选择概率。该损失越小，说明实际负载越接近均匀分布。

5. PyTorch 逻辑实现

下面给出一个简洁但完整的 MoE 层实现，包含路由、Top-K 选择、专家计算和加权聚合。

import torch
import torch.nn as nn
import torch.nn.functional as F

class MoELayer(nn.Module):
    def __init__(self, hidden_dim, ffn_dim, num_experts, top_k=2):
        super().__init__()
        self.num_experts = num_experts
        self.top_k = top_k

        # 门控网络：将 hidden state 映射到专家得分
        self.gate = nn.Linear(hidden_dim, num_experts, bias=False)

        # N 个独立专家，每个都是标准 FFN
        self.experts = nn.ModuleList([
            nn.Sequential(
                nn.Linear(hidden_dim, ffn_dim),
                nn.GELU(),
                nn.Linear(ffn_dim, hidden_dim),
            ) for _ in range(num_experts)
        ])

    def forward(self, x):
        # x: [batch * seq_len, hidden_dim]

        # 1. 计算路由分数
        gate_logits = self.gate(x)                # [B, N]
        gate_probs = F.softmax(gate_logits, dim=-1) # [B, N]

        # 2. Top-K 选择
        topk_weights, topk_indices = torch.topk(gate_probs, self.top_k, dim=-1)
        topk_weights = topk_weights / topk_weights.sum(dim=-1, keepdim=True)

        # 3. 专家计算 + 加权聚合
        output = torch.zeros_like(x)
        for k in range(self.top_k):
            expert_idx = topk_indices[:, k]        # [B]
            weight = topk_weights[:, k].unsqueeze(-1)  # [B, 1]

            for e in range(self.num_experts):
                mask = (expert_idx == e)
                if mask.any():
                    expert_input = x[mask]
                    expert_out = self.experts[e](expert_input)
                    output[mask] += weight[mask] * expert_out

        return output

5.1 负载均衡损失的实现

def load_balance_loss(router_probs, expert_indices, num_experts):
    # router_probs: [B, num_experts]
    # expert_indices: [B, top_k]
    batch_size = router_probs.size(0)

    # 统计每个专家实际接收到的 token 数量
    freq = torch.zeros(batch_size, num_experts, device=router_probs.device)
    freq.scatter_add_(
        1,
        expert_indices,
        torch.ones_like(expert_indices, dtype=torch.float)
    )

    avg_prob = router_probs.mean(dim=0)      # [N]
    avg_freq = freq.mean(dim=0)              # [N]

    return num_experts * torch.sum(avg_freq * avg_prob)

5.2 容量裁剪

def apply_capacity(expert_indices, capacity_factor, num_experts):
    batch_size = expert_indices.size(0)
    capacity = int((batch_size / num_experts) * capacity_factor)

    # 对每个专家，只保留前 capacity 个 token
    counts = torch.zeros(num_experts, dtype=torch.long)
    mask = torch.zeros_like(expert_indices, dtype=torch.bool)

    for i in range(batch_size):
        for k in range(expert_indices.size(1)):
            e = expert_indices[i, k].item()
            if counts[e] < capacity:
                mask[i, k] = True
                counts[e] += 1

    return mask  # 超出容量的位置为 False

6. 专家并行与通信

当专家数量很多时，单个设备无法容纳所有专家参数，因此需要 专家并行（Expert Parallelism, EP）。不同专家被放置在不同设备上，每个 token 根据 Router 结果通过 All-to-All 通信发送到对应设备。

专家并行的通信流程分为两个阶段：

  1. Dispatch（分发）：每个设备根据本地 Router 结果，把 token 发送到拥有对应专家的设备；
  2. Combine（合并）：各设备完成专家计算后，把结果通过 All-to-All 发回原始设备，按权重聚合。

关键观察：MoE 的训练/推理吞吐不仅取决于 FLOPs，更取决于 All-to-All 通信延迟。EP 分组大小、负载均衡、容量因子和通信压缩策略是工程优化的核心。

7. 应用场景与挑战

7.1 典型应用场景

场景 说明
大语言模型 DeepSeek-V2/V3、Mixtral 8x7B、GShard 等使用 MoE 扩展模型容量
多任务学习 不同专家学习不同任务或领域的特征表示
多模态模型 为图像、文本、音频等不同模态分配不同专家
推荐系统 不同专家学习不同用户群体或商品类别的模式

7.2 主要挑战

  • 训练不稳定性：Router 容易出现收敛困难、专家坍缩（所有 token 偏向少数专家）等问题；
  • 负载不均衡：某些专家可能过载，导致容量溢出和性能下降；
  • 通信开销：专家并行引入大量 All-to-All 通信，对网络带宽和拓扑敏感；
  • 显存碎片：不同批次分配到各专家的 token 数动态变化，容易导致显存使用不均衡；
  • 推理调度复杂：动态路由增加了服务化部署中的 batching 和调度难度。

8. 总结

MoE 混合专家网络通过稀疏激活和条件计算，在不显著增加单次推理计算量的前提下，大幅扩展了模型容量。其核心组件包括：

  • 多个独立的专家网络（Experts）
  • 决定路由的门控网络（Router）
  • 只激活 Top-K 个专家的选择机制

工程实践中，负载均衡损失、容量因子和专家并行是 MoE 能够高效训练和部署的三大关键。在 vLLM-Ascend 等 NPU 场景中，还需要特别关注 All-to-All 通信优化、NPU 内存碎片化以及动态路由带来的调度开销。

一句话概括：MoE 用"多个专家 + 动态路由"替代"单一稠密网络"，让模型在参数更多、能力更强的同时，保持每次推理的计算成本基本可控。
