② 各 Manager 的 find_longest_cache_hit 逐行逻辑

FullAttentionManager (上游) 上游复用

查找逻辑

1
block_size = spec.block_size，若 DCP>1 则 block_size *= dcp_world_size
2
max_num_blocks = max_length // block_size
3
遍历 block_hashes[:max_num_blocks]（链式哈希）
4
每个 hash 调用 block_pool.get_cached_block(hash, group_ids)
5
命中 → computed.append(cached_block)，继续下一个
6
未命中 → break（链式哈希保证后续必不命中）
7
EAGLE: computed.pop() 丢弃最后一个 block
8
alignment 截断: 确保 len × block_size % alignment == 0

特点

  • 物理块级查找：每个 hash 对应一个物理 block
  • 向下闭包：命中 N 个 block → 前 N-1 个必也命中
  • Coordinator 利用此特性：首次查完后后续迭代仅截断，不重新查
  • 无需逻辑块聚合

CompressAttentionManager (Ascend 继承) 继承 FullAttentionManager

查找逻辑

1
block_size = spec.block_size，若 DCP>1 则 ×= dcp
2
★ 关键差异：logical_block_size = block_size × compress_ratio
3
★ BlockHashListWithBlockSize：把物理级 hash_block_size 的哈希聚合为按 logical_block_size 的迭代器
4
max_num_blocks = max_length // logical_block_size
5
遍历 logical_block_hashes[:max_num_blocks]
6
每个逻辑块 hash → block_pool.get_cached_block()
7
命中 → append，未命中 → break
8
EAGLE pop + alignment 截断（同上游）

为什么用逻辑块？

压缩 MLA 的 KV 以 block_size × compress_ratio 为单位存储和共享。若按物理 block_size 查找，一个逻辑块内的部分修改不会被检测到，导致误命中。

SlidingWindowManager (上游) 上游复用

查找逻辑

1
同 FullAttention：链式 get_cached_block 查找
2
★ 差异：null_block 占位 — 前面不可达的 block（超出 sliding_window 范围）用 null_block 填充
3
get_num_skipped_tokens() 计算被跳过的 token 数
4
block 回收：超出窗口的旧 block 可被释放复用

特点

  • 只缓存窗口内可达的 block
  • 不可达 block → null_block 占位（block_id=-1）
  • slot_mapping 对 null_block 返回 PAD_SLOT_ID
  • Admission cap: 限制每请求最大 block 数

AscendMambaManager (Ascend Patch) Patch MambaManager

查找逻辑

1
find_longest_cache_hit：直接委托父类 MambaManager
2
Mamba 是状态空间模型，KV cache 是递推状态，非链式哈希
3
★ Patch 修改点：get_num_blocks_to_allocate 补 +1 block
4
修复外部 KV cache 同步加载时少分配 1 个 block 的 bug

特点

  • Mamba block_size 不乘 DCP（状态不分片）
  • enable_partial_hash_hits: block_size > hash_block_size 时启用
  • mamba_cache_mode = "align" 时对齐到 hash_block_size

③ cache_blocks · 写入 Prefix Cache 全局索引

写入时机：Scheduler.update_from_output() 中调用 关键写入点

FullAttentionManager.cache_blocks (上游)

1
num_full_blocks = num_tokens // block_size
2
跳过已缓存：if num_cached_blocks >= num_full_blocks: return
3
block_pool.cache_full_blocks(request, blocks, num_cached, num_full, block_size)

CompressAttentionManager.cache_blocks (Ascend) 差异

1
★ num_full_blocks = num_tokens // (block_size × compress_ratio)
2
只缓存完整逻辑块！未满的不写入
3
block_pool.cache_full_blocks(..., block_size=block_size × compress_ratio)
4
alignment_tokens 参数被忽略（逻辑块已自然对齐）

BlockPool.cache_full_blocks 内部逻辑 (上游)

1
遍历 blocks[num_cached_blocks : num_full_blocks]
2
对每个 block，从 request.block_hashes 取对应 hash
3
★ 注册到全局索引：cached_block_hash_to_id[hash] = block.block_id
4
设置 block.ref_cnt，标记 block 已被缓存
5
后续请求通过 get_cached_block(hash) 即可找到此 block

⑤ AscendHybridKVCacheCoordinator 不动点迭代

多 group 协调算法 Ascend 自维护

不同 attention group（Full / Compress / SWA / Mamba）各有自己的 block_size 和命中长度。Coordinator 需要找到一个所有 group 都能命中的统一长度。

effective_block_size 计算

  • Mamba: block_size（不乘 DCP）
  • 其他: block_size × DCP
  • 有 compress_ratio: × compress_ratio

简单 hybrid 优化

  • 1 Full + 1 Other → 一次迭代即收敛
  • Full 首次查完后仅截断
  • is_simple_hybrid → break

Partial-group hit

  • 各 group hit 不一致
  • min(per_group_hits) < fa_hit
  • PD 场景: 结合远端 connector 判断
