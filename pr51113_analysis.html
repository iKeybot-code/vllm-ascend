vLLM PR #51113 改动分析

主题：Keep mamba align prefill chunks block-aligned past last_cache_position
作者：ivanium（基于 kodek #45477、yanghui1-arch #47861 的工作）
合并者：njhill | 状态：已合并至 main
原文链接：https://github.com/vllm-project/vllm/pull/51113

一、一句话总结

修复了 hybrid Mamba/GDN 模型在 mamba_cache_mode="align" 模式下、启用 EAGLE/MTP 投机解码时的 前缀缓存污染（prefix-cache poisoning）问题： 非最终的 prefill chunk 现在必须在 mamba block 边界结束，避免把"截断状态"当作"完整块状态"缓存，导致后续请求恢复出错状态。

二、核心概念速览

术语含义
Mamba / GDN状态空间模型（SSM）/ Gated Delta Net，一类循环层，状态按固定 block 写入缓存
mamba_cache_mode="align"mamba 状态缓存按 block 对齐，slot p 应该保存第 (p+1)*block_size 个 token 之后的状态
EAGLE / MTP投机解码技术，MTP 会预瞻若干 token，导致 last_cache_position 被提前一个 block
last_cache_position调度器认为"还能被后续请求命中"的最大 token 位置
prefill_end本次 prefill 实际结束位置（max(num_prompt_tokens, num_tokens - 1)）

三、问题背景：为什么需要这个修复？

3.1 关键不变量（Invariant）

slot p 必须保存恰好第 (p + 1) × block_size 个 token 之后的状态。
例如 block_size = 1600 时，slot 0 保存 state@1600，slot 1 保存 state@3200，依此类推。

这个不变量是 prefix caching 的基础：后续请求如果命中 slot p，就期望拿到 state@(p+1)*block_size。

3.2 旧的漏洞

在旧的 _mamba_block_aligned_split 中，只有在 end < last_cache_position 时才强制 chunk 在 block 边界结束。 超过 last_cache_position 后，任何 chunk end 都被接受。

当启用 EAGLE/MTP 时，last_cache_position 会被回退一个 block（并且短于两个 mamba block 的 prompt 会被置 0）。 于是出现如下场景：

  1. 多个 prefill 并发竞争 token budget；某个请求的第一个 chunk 只运行了 364 token，在 mid-block 处结束。
  2. 这个 chunk end 把 slot 0 写成了 state@364（而不是 state@1600）。
  3. 下一个 chunk 跨过了 1600，调度器把 slot 0 当作 state@1600 发布到 prefix cache。
  4. 后续请求命中这个 slot 时，恢复的是一个被截断的状态，输出错 token；没有报错，没有日志。
危害： 无崩溃、无异常、HTTP 200，但生成内容错误。且只在并发/混合长度请求下出现，单请求场景反而"恰好安全"，因此极难定位。

四、代码改动详解

4.1 改动文件

  • vllm/v1/core/sched/scheduler.py：修复核心逻辑
  • tests/v1/core/test_mamba_align_chunk_split.py：新增回归测试

4.2 关键代码变化

修改前：

if start >= max(request.num_prompt_tokens, request.num_tokens - 1):
    return num_new_tokens

# ...

end = start + num_new_tokens
if end < last_cache_position:
    # 强制 block 对齐
    ...

stops = (
    next_block_boundary
    if start % block_size != 0 and next_block_boundary <= last_cache_position
    else 0,
    last_cache_position,
    ...
)

修改后：

prefill_end = max(request.num_prompt_tokens, request.num_tokens - 1)
if start >= prefill_end:
    return num_new_tokens

# ...

end = start + num_new_tokens
# 不变量：slot p 保存 (p+1)*block_size 的状态
# 只有 prefill 的最后一个 chunk 可以不落在 block 边界
if end < prefill_end:
    # 强制 block 对齐
    ...

stops = (
    # mid-block 开始的 chunk 必须在下一个边界停止
    next_block_boundary if start % block_size != 0 else 0,
    last_cache_position,
    ...
)

4.3 三个关键点

改动作用
prefill_end 替代 last_cache_position 作为对齐门槛 只有 prefill 的最后一个 chunk 才允许在非 block 边界结束；其余所有中间 chunk 必须对齐
删除 next_block_boundary <= last_cache_position 条件 只要 chunk 从 mid-block 开始，无论是否超过 last_cache_position，都必须先对齐到下一个 block 边界
保留 last_cache_position 作为强制 stop 它仍然服务命中率：当等长请求的 EAGLE 回退命中真实落点时，能在这里物化一个 snapshot

六、为什么这个 bug 难发现？

  • 无症状： 不崩溃、不报错、HTTP 200，只是生成 token 错误。
  • 单请求安全： 低位的 slot 是 null block，cache_full_blocks 会跳过，所以单测无法触发。
  • 并发/混合长度才触发： 需要多个请求共享 prefix，且某个较长请求的命中能到达被污染的 slot。
  • EAGLE/MTP 改变 last_cache_position： 引入了原本不存在的"未保护区域"。

七、对开发者的启示

  1. 缓存不变量必须全局保持： 不要只在"看起来会被命中"的范围内才维护。
  2. 投机解码会改变调度语义： 任何依赖 last_cache_position 的逻辑都要考虑 EAGLE/MTP 的回退。
  3. 并发测试是必需的： 很多 correctness bug 只在多请求共享 prefix 时出现。
  4. 新 bug 可能表现为"无异常但结果错"： 对状态敏感的结构（Mamba/GDN/SSM）要格外警惕。

八、原文核心引用

"A single request is accidentally safe — its low slots are null blocks, which cache_full_blocks skips — which is why this only appears under concurrency and was hard to pin down."
"Every request resuming from that hash silently restores a truncated state. Nothing raises, nothing logs, and the entry persists until restart."
