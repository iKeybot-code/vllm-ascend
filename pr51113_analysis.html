vLLM PR #51113 改动分析

主题：Keep mamba align prefill chunks block-aligned past last_cache_position
作者：ivanium（基于 kodek #45477、yanghui1-arch #47861 的工作）
合并者：njhill | 状态：已合并至 main
原文链接：https://github.com/vllm-project/vllm/pull/51113

一、一句话总结

修复了 hybrid Mamba/GDN 模型在 mamba_cache_mode="align" 模式下、启用 EAGLE/MTP 投机解码时的 前缀缓存污染（prefix-cache poisoning）问题： 非最终的 prefill chunk 现在必须在 mamba block 边界结束，避免把"截断状态"当作"完整块状态"缓存，导致后续请求恢复出错状态。

二、核心概念速览

术语含义
Mamba / GDN状态空间模型（SSM）/ Gated Delta Net，一类循环层，状态按固定 block 写入缓存
mamba_cache_mode="align"mamba 状态缓存按 block 对齐，slot p 应该保存第 (p+1)*block_size 个 token 之后的状态
EAGLE / MTP投机解码技术，MTP 会预瞻若干 token，导致 last_cache_position 被提前一个 block
last_cache_position调度器认为"还能被后续请求命中"的最大 token 位置
prefill_end本次 prefill 实际结束位置（max(num_prompt_tokens, num_tokens - 1)）

三、问题背景：为什么需要这个修复？

3.1 关键不变量（Invariant）

slot p 必须保存恰好第 (p + 1) × block_size 个 token 之后的状态。
例如 block_size = 1600 时，slot 0 保存 state@1600，slot 1 保存 state@3200，依此类推。

这个不变量是 prefix caching 的基础：后续请求如果命中 slot p，就期望拿到 state@(p+1)*block_size。

3.2 旧的漏洞

在旧的 _mamba_block_aligned_split 中，只有在 end < last_cache_position 时才强制 chunk 在 block 边界结束。 超过 last_cache_position 后，任何 chunk end 都被接受。

当启用 EAGLE/MTP 时，last_cache_position 会被回退一个 block（并且短于两个 mamba block 的 prompt 会被置 0）。 于是出现如下场景：

  1. 多个 prefill 并发竞争 token budget；某个请求的第一个 chunk 只运行了 364 token，在 mid-block 处结束。
  2. 这个 chunk end 把 slot 0 写成了 state@364（而不是 state@1600）。
  3. 下一个 chunk 跨过了 1600，调度器把 slot 0 当作 state@1600 发布到 prefix cache。
  4. 后续请求命中这个 slot 时，恢复的是一个被截断的状态，输出错 token；没有报错，没有日志。
危害： 无崩溃、无异常、HTTP 200，但生成内容错误。且只在并发/混合长度请求下出现，单请求场景反而"恰好安全"，因此极难定位。

四、代码改动详解

4.1 改动文件

  • vllm/v1/core/sched/scheduler.py：修复核心逻辑
  • tests/v1/core/test_mamba_align_chunk_split.py：新增回归测试

4.2 关键代码变化

修改前：

if start >= max(request.num_prompt_tokens, request.num_tokens - 1):
    return num_new_tokens

# ...

end = start + num_new_tokens
if end < last_cache_position:
    # 强制 block 对齐
    ...

stops = (
    next_block_boundary
    if start % block_size != 0 and next_block_boundary <= last_cache_position
    else 0,
    last_cache_position,
    ...
)

修改后：

prefill_end = max(request.num_prompt_tokens, request.num_tokens - 1)
if start >= prefill_end:
    return num_new_tokens

# ...

end = start + num_new_tokens
# 不变量：slot p 保存 (p+1)*block_size 的状态
# 只有 prefill 的最后一个 chunk 可以不落在 block 边界
if end < prefill_end:
    # 强制 block 对齐
    ...

stops = (
    # mid-block 开始的 chunk 必须在下一个边界停止
    next_block_boundary if start % block_size != 0 else 0,
    last_cache_position,
    ...
)

4.3 三个关键点

改动作用
prefill_end 替代 last_cache_position 作为对齐门槛 只有 prefill 的最后一个 chunk 才允许在非 block 边界结束；其余所有中间 chunk 必须对齐
删除 next_block_boundary <= last_cache_position 条件 只要 chunk 从 mid-block 开始，无论是否超过 last_cache_position，都必须先对齐到下一个 block 边界
保留 last_cache_position 作为强制 stop 它仍然服务命中率：当等长请求的 EAGLE 回退命中真实落点时，能在这里物化一个 snapshot

六、为什么这个 bug 难发现？

  • 无症状： 不崩溃、不报错、HTTP 200，只是生成 token 错误。
  • 单请求安全： 低位的 slot 是 null block，cache_full_blocks 会跳过，所以单测无法触发。
  • 并发/混合长度才触发： 需要多个请求共享 prefix，且某个较长请求的命中能到达被污染的 slot。
  • EAGLE/MTP 改变 last_cache_position： 引入了原本不存在的"未保护区域"。

七、对开发者的启示

  1. 缓存不变量必须全局保持： 不要只在"看起来会被命中"的范围内才维护。
  2. 投机解码会改变调度语义： 任何依赖 last_cache_position 的逻辑都要考虑 EAGLE/MTP 的回退。
  3. 并发测试是必需的： 很多 correctness bug 只在多请求共享 prefix 时出现。
  4. 新 bug 可能表现为"无异常但结果错"： 对状态敏感的结构（Mamba/GDN/SSM）要格外警惕。

八、PD 分离 + dspark 的真实根因：prefill 对齐逻辑错误地进入了 decode 路径

8.1 场景还原

在 PD（Prefill-Decode）分离架构中，P 节点负责长 prompt 的 prefill，D 节点只负责逐 token decode。 P 节点把 KV/Mamba 状态传给 D 节点后，D 节点每次只收到 1 个新 token，并把它和 D 节点上其他纯 decode 请求一起 batch 推理。

此时如果 D 节点还开着 dspark（或 EAGLE/MTP）投机解码，会发生：

  • dspark 需要为每个请求计算若干草稿 token（如 7 个）；
  • 为了计算/验证这些草稿，D 节点调度器会为该请求分配一定数量的 token 预算（如 5 个）；
  • 但 _mamba_block_aligned_split 一看到 end < prefill_end，就认为"这个请求还有 prefill 没做完"，强制把 chunk end 对齐到下一个 mamba block 边界。

8.2 根因：调度器没有区分 "P 节点 prefill" 和 "D 节点 decode"

以具体数字为例：

  • prompt 长度 380，投机 token 数 7，mamba block_size = 384
  • prefill_end = max(380, 380 + 7 - 1) = 386
  • D 节点收到 P 节点传过来的 1 个 token，从位置 380 继续
  • 若预算为 5，则 end = 385，而 385 < 386

新逻辑触发强制对齐：下一个 block 边界是 384，于是 chunk 被截断为只处理 4 个 token（380→384）， 剩下 1 个 token 预算被浪费，dspark 算草稿时发现实际可处理的 token 数（4）和原本预期的草稿长度不兼容， 只能回退草稿数量，严重时直接破坏投机解码流水线。

根因一句话：
_mamba_block_aligned_split 是为 P 节点 prefill 阶段维护 mamba 缓存不变量而设计的对齐逻辑， 却被无差别地应用到了 D 节点的 decode 路径上，而 decode 阶段本不该再受 prefill 块边界约束。

8.3 为什么修改前没有这个问题？

旧逻辑是 if end < last_cache_position:，在 EAGLE/MTP 场景下 last_cache_position 会被回退一个 block， 短于两个 block 时甚至被置 0。因此 end < last_cache_position 不成立，对齐逻辑不触发，D 节点的 5 个预算能完整使用。

代价是：旧逻辑不会强制中间 chunk 在 block 边界结束，导致 slot 被污染（这正是 #51113 修复的 bug）。 新 PR 用 prefill_end 扩大了强制对齐范围，堵住了污染漏洞，却把 D 节点的 decode 路径也卷了进来。

8.4 最优解决方案

核心原则：prefill 阶段需要 block 对齐以保证缓存不变量；decode 阶段不应该再触发 prefill 块对齐。

方案 A（推荐）：按阶段条件化对齐逻辑

# 仅在请求仍处于 prefill 阶段时强制 block 对齐
# decode 阶段（D 节点或已转为 decode 的请求）直接返回 num_new_tokens
if request.is_prefill() and end < prefill_end:
    # 强制 block 对齐
    ...

这是最干净、语义最清晰的改法。_mamba_block_aligned_split 的职责本来就是服务 prefill 阶段的 mamba 缓存对齐， decode 阶段没有新的 mamba 状态需要写入 prefix cache，自然不该被截断。

方案 B：保留 last_cache_position 作为对齐门槛

if end < last_cache_position:
    # 强制 block 对齐
    ...

这是 #51113 修改前的逻辑。它能避免 D 节点 decode 预算被截断，但会重新引入 prefix-cache poisoning 问题（即 #51113 要修复的 bug）。 因此单独回退不可行，最多只能作为组合方案的一部分。

方案 C：引入 "decode_phase_budget_preserved" 标记

if request.state == RequestState.DECODE:
    return num_new_tokens
if end < prefill_end:
    # 强制 block 对齐
    ...

如果 vLLM 的调度模型里没有现成的 prefill/decode 阶段标记，可以显式加一个；但这会扩大改动范围，不如方案 A 自然。

8.5 方案对比

方案优点缺点推荐度
A：按 request.is_prefill() 条件化 语义清晰、改动最小、同时保留 #51113 的不变量 需要确认 vLLM 调度器里阶段标记的可用性 ⭐⭐⭐ 首选
B：回退到 last_cache_position 门槛 改动最小 重新引入 prefix-cache poisoning ❌ 不可单独使用
C：显式阶段标记 精确、可控 改动范围大，可能 touching 多个模块 ⭐⭐ 备选

8.6 关键结论

  1. #51113 修复了 P 节点 prefill 阶段的缓存污染，但副作用是把对齐逻辑延伸到了 D 节点 decode 路径；
  2. PD 分离场景下，D 节点每次只处理 1 个新 token，强制 prefill 块对齐会吃掉 dspark 草稿 token 的预算；
  3. 最优修复是在 _mamba_block_aligned_split 中按请求阶段做条件化，decode 阶段直接放行；
  4. 这不是简单回退 #51113，而是要在保持 P 节点不变量的前提下，把 D 节点从 prefill 对齐逻辑中解放出来。
